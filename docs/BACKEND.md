# الخادم وقواعد العمل

## طبقات العمل

Route Handler يستقبل الطلب ويثبت الجلسة ويتحقق من Zod، ثم يستدعي خدمة domain، ثم adapter قاعدة البيانات. لا منطق مالي داخل React. كل mutation يتحقق من الهوية والصلاحية في الخادم وداخل RPC عند استخدامها. بيانات العميل لا تحدد الدور أو user_id أو سعر الوحدة.

قراءات صفحات الخادم تستدعي الخدمات مباشرة دون HTTP داخلي. mutations تستخدم العقود في [API_CONTRACTS](API_CONTRACTS.md). يمكن استعمال Server Actions كواجهة رقيقة للخدمات نفسها عندما يفيد النموذج، مع نفس التحقق.

## الأموال والتسعير

كل الأسعار بوحدات صحيحة كما في [DATABASE](DATABASE.md). `subtotal = sum(unit_price * quantity)`. كوبون واحد على المنتجات فقط؛ لا خصم على التوصيل. بالنسبة المئوية: `floor(subtotal * percent / 100)` ثم سقف max_discount إن وجد. الخصم الثابت يُحد إلى subtotal، ويطبق حد الطلب الأدنى على subtotal قبل الخصم. `total = subtotal - discount + shipping`.

Quote يعيد الإجمالي والعملة والرسوم و`quoteHash` كـtoken موقّع حسب API_CONTRACTS. `place_order` يعيد الحساب تحت القفل ويقارن بيانات العرض التي تحقق الخادم من توقيعها؛ إذا تغير السعر/الكوبون/رسوم الشحن يعيد PRICE_CHANGED بلا إنشاء. لا ترسل سعر العميل كحقيقة. حد 20 SKU مختلفًا و10 وحدات لكل SKU في الطلب كبداية قابلة للضبط.

## إنشاء الطلب الآمن

1. تحقق جلسة العميل والبريد المؤكد، نفس origin، حجم payload، حدود المعدل، صيغة الهاتف ومنطقة الشحن.
2. احسب canonical request hash بعد ترتيب العناصر، من العنوان والعناصر والكوبون وquote_hash. لا تسجل محتواه الشخصي في logs.
3. داخل المعاملة احصل على قفل خاص بـuser/idempotency. إذا يوجد طلب بنفس المفتاح ونفس hash أعده فورًا؛ مع payload مختلف أعد IDEMPOTENCY_CONFLICT.
4. اقرأ المنتجات المنشورة وvariants النشطة واقفل variants بترتيب موحد؛ اقفل الكوبون إن وجد. راجع المخزون والصلاحية وحدود الكوبون تحت القفل.
5. اكتب order/items/snapshots، اخصم stock_available، أضف inventory movements وcoupon redemption وstatus history وnotification_outbox في المعاملة نفسها.
6. Commit ثم HTTP 201. إذا انقطع الرد، retry بنفس المفتاح يستعيد الطلب. لا تربط نجاح الطلب باستجابة Telegram.

التعامل مع deadlock/serialization failure: أعد المحاولة داخليًا حتى مرتين بتأخير قصير وبنفس المفتاح، ثم خطأ قابل للمحاولة. UNIQUE constraints خط الدفاع الأخير، لكنها لا تغني عن ترتيب الأقفال والذرية.

## دورة الطلب

| من | إلى | الشروط والأثر |
|---|---|---|
| new | confirmed | موظف الطلبات أو المدير، تحقق توفر بيانات التنفيذ |
| confirmed | preparing | نفس الصلاحية |
| preparing | shipped | تسجيل ملاحظة التسليم للشحن إن وجدت |
| shipped | delivered | تأكيد تحصيل النقد، cod_status=collected ووقت/موظف التحصيل |
| new/confirmed/preparing | cancelled | سبب إلزامي؛ release stock + coupon مرة واحدة؛ cod_status=not_due |
| shipped | returned | سبب رفض/فشل التسليم، cod_status=not_due؛ لا زيادة مخزون تلقائيًا |

الحالات delivered/cancelled/returned نهائية في النسخة الأولى. المرتجع يعاد للمخزون عبر `adjust_inventory` بسبب return_restock وربط order مع event_key فريد بعد الاستلام والفحص. المرتجعات بعد التسليم والتعويضات المالية خارج النطاق. لا زر رجوع عشوائي بين الحالات. لا تعدل items أو العنوان بعد الإنشاء في النسخة الأولى؛ الطلب الخاطئ يلغى قبل الشحن ويعاد إنشاؤه.

## Telegram outbox

بعد حفظ الطلب، يحاول الخادم إرسال إشعاره باستخدام `after()` إن كان bot token مضبوطًا. توجد أيضًا مهمة Vercel يومية عند 02:00 UTC في `vercel.json` لمعالجة outbox دون زيارة مستخدم؛ **إعادة المحاولة قد تتأخر حتى التشغيل اليومي** على إعداد Hobby. للتشغيل كل دقيقة يلزم مجدول مؤهل أو Supabase Cron آمن. يحمي `CRON_SECRET` endpoint العامل. يسحب العامل حتى 20 سجلًا مستحقًا ويضع lease لمدة دقيقتين، ثم يسجل message_id. يستعيد السجل بعد انتهاء lease إذا مات العامل. مهلة الطلب الخارجي 10 ثوانٍ؛ timeout خارجي بعد قبول Telegram قد يسبب تكرار رسالة، ولذلك الضمان at-least-once لا exactly-once؛ رقم الطلب ظاهر لتعرف النسخ.

المحاولات: 5 مع انتظار 1، 5، 15، 60 دقيقة بعد الإخفاقات المتعاقبة؛ احترم retry_after عند 429. خطأ دائم كقناة غير صحيحة يوقف ويظهر failed؛ المدير يراجع الإعداد ويعيد enqueue. لا retry غير محدود. تعطيل Telegram يحتفظ بالطلبات ويظهر الإشعارات المتوقفة؛ إعادة التفعيل تعيد جدولة آخر الطلبات عبر إجراء صريح.

الرسالة الافتراضية: رقم الطلب + العناصر + الإجمالي والعملة + COD + المدينة + رابط صفحة الإدارة المحمية. التفاصيل الكاملة للهاتف والعنوان اختيار Manager لقناة خاصة فقط. لا رابط عام يسمح بعرض الطلب. استخدم plain text أو escaping كامل لـHTML، واقطع الحقول وفق حد الرسالة. لا صور أو مرفقات مطلوبة. [مرجع sendMessage](https://core.telegram.org/bots/api#sendmessage).

## Gemini

الخادم فقط يستدعي API بعد إكمال الحساب. مهلة 8 ثوانٍ، محاولة إضافية واحدة فقط لخطأ عابر إذا بقي زمن كافٍ؛ إجمالي انتظار ≤12 ثانية ثم fallback. ضع حدًا للمخرجات وتحقق من اللغة والبنية والطول والمعرفات. لا أدوات ولا browsing ولا function calling لهذا التكامل. لا بيانات عنوان/هاتف/اسم شخص. تفاصيل schema والتحقق في [RECOMMENDATION](RECOMMENDATION.md).

## التخزين والصور

رفع صور WebP/JPEG/PNG فقط، حد مبدئي 5MB، MIME وتوقيع فعلي، حد أبعاد، أسماء عشوائية. رفض SVG غير المنقح والملفات التنفيذية. استخراج صورة محسنة وإزالة metadata غير اللازمة. الأصول المنشورة عامة، draft في bucket خاص إلى النشر. تغيير صورة لا يحذف الصورة القديمة التي ما زال مرجع قائم يستخدمها. Manager وinventory_manager فقط يرفعان الصور.

## المراقبة والحدود

request_id ثابت عبر الطلب والسجلات. سجل latency وerror code وحجم دفعة outbox ومصدر الشرح وعدد النتائج بدون PII. عدادات معدل في DB بزيادة ذرية؛ لا memory-only limit في serverless. افتراض بداية: quote 30/min، checkout 5/min لكل حساب و20/min لكل IP، quiz completion 5/hour لكل مالك و20/hour لكل IP. HMAC للـIP بملح سري وتنظيف دوري؛ الحدود قابلة للمراجعة بعد تجربة فعلية. أعد 429 مع retryAfterSeconds.

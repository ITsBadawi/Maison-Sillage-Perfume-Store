# الإعداد والنشر

## ما هو موجود الآن؟

التطبيق يعمل محليًا على Supabase CLI وDocker مع بيانات ديمو فعلية، وقد اختُبرت عمليات المتجر والحسابات والأدوار. لا توجد بعد بيئة demo منشورة، ولا مفاتيح Gemini أو Telegram في المشروع. لا تعدّ اختبارات المحاكاة إثباتًا لوصول رسالة إلى قناة حقيقية أو توليد شرح حي من Gemini.

## البيئات

| البيئة | قاعدة البيانات | الاستخدام |
|---|---|---|
| local | Supabase محلي عبر CLI وDocker إن متاح | التطوير والاختبارات وإعادة seed |
| demo | مشروع Supabase مستقل + Vercel deployment | عرض الوكالة ببيانات خيالية وخدمات حقيقية |
| production لاحقًا | مشروع وsecrets منفصلة | متجر صاحب النشاط بعد مراجعة جاهزيته |

Preview لا يتصل ببيانات production. لا تنسخ عناوين العملاء إلى seed. لكل بيئة مفاتيح وقناة إشعارات مستقلة. عند تعذر Docker يمكن تطوير واجهة أولية، لكن اختبارات DB تحتاج بيئة معزولة قبل اعتماد المرحلة.

## التشغيل المحلي

1. ثبّت Node.js متوافقًا مع `package.json` وDocker Desktop، ثم نفّذ `npm ci` و`npx supabase start` داخل مجلد المشروع.
2. انسخ `.env.example` إلى `.env.local` محليًا. استخرج URL والمفتاح العام والمفتاح السري من `npx supabase status`، وضعها في المتغيرات المناسبة. ولّد `QUOTE_SIGNING_SECRET` و`RATE_LIMIT_SALT` عشوائيين. لا تنسخ مفاتيح بيئة أخرى.
3. نفّذ `npx supabase db reset --local` لتطبيق جميع migrations وseed. **هذا الأمر يمسح قاعدة Supabase المحلية الخاصة بالمشروع**؛ استخدمه فقط عندما تكون البيانات المحلية قابلة للإزالة. لا تستخدم `--linked` أو reset على مشروع بعيد.
4. نفّذ `npm run demo:staff` مرة واحدة بعد reset. يُنشئ ثلاث حسابات موظفين محلية بكلمات مرور عشوائية في `demo-credentials.local.json` المستبعد من التوزيع. إذا أعدت ضبط القاعدة، احذف هذا الملف المحلي القديم ثم أعد الأمر؛ لا تنقل الملف إلى الأرشيف أو المستودع.
5. نفّذ `npm run dev` وافتح `/ar` أو `/en`. فحوصات الكود: `npm run lint` و`npm run typecheck` و`npm test` و`npm run build`. اختبارات المتصفح المتصلة بقاعدة محلية تستخدم `RUN_SUPABASE_E2E=1` مع `npm run test:e2e`.

## إعداد الخدمات للعرض

### Supabase

أنشئ مشروع demo مستقل في منطقة ملائمة للاستضافة. طبق migrations بنفس ترتيب الاختبار، ثم RLS وgrants وStorage policies. اضبط site URL وredirect URLs للـAuth محليًا وللنطاق النهائي، مع قائمة دقيقة لا wildcard عامة. فعّل تأكيد البريد وإعداد SMTP صالح للعرض المنشور؛ جرّب التسجيل والاستعادة فعليًا. إعداد SMTP عبر مزود مناسب جزء من التشغيل وليس تكامل تسويقي جديدًا.

المفاتيح العامة من Connect dialog؛ مفتاح secret على الخادم فقط. لا تعرض حساب Supabase نفسه للزبون؛ واجهة الإدارة هي وسيلة الاستخدام. راجع advisories المناسبة للصلاحيات والأداء قبل النشر.

### Gemini

احصل على API key لحساب العرض وضعه على الخادم. اختر model مستقرًا متاحًا للحساب من [قائمة Google](https://ai.google.dev/gemini-api/docs/models) وجرّب structured output باللغة العربية والإنجليزية. لا تعتمد الاسم المذكور في محادثة قديمة. ضع حد إنفاق/إنذار حسب إمكانات الحساب، واختبر fallback قبل العرض.

### Telegram

أنشئ bot عبر BotFather وقناة خاصة للديمو، وأضف البوت بالصلاحية اللازمة للنشر. ضع token في بيئة الخادم وchat_id في الإعدادات المحمية. جرّب رسالة اختبار بلا بيانات شخصية، ثم طلبًا حقيقيًا ببيانات خيالية. لا يحتاج المشروع إلى استقبال رسائل Telegram أو webhook في النسخة الأولى.

### Vercel

اربط المستودع بالمشروع واضبط env على Development/Preview/Production كلٌ حسب حاجته. اضبط build الموثق وإصدار Node المتوافق، ثم URL الصحيح لـAuth وNEXT_PUBLIC_APP_URL. المتغيرات العامة قد تتطلب rebuild عند التغيير؛ لا تكتفِ بتعديلها بعد البناء.

يرسل الخادم الإشعار بعد حفظ الطلب مباشرة عبر `after()` إن كان bot token مضبوطًا؛ فشل الإرسال لا يلغي الطلب ويتركه في outbox. يحوي `vercel.json` مهمة احتياطية يومية عند 02:00 UTC؛ هذا يناسب حد Vercel Hobby الحالي ولا يعني أن إعادة المحاولة ستحدث خلال دقائق. إذا تطلب العرض إعادة محاولة أسرع، اضبط Supabase Cron آمنًا لاستدعاء endpoint العامل أو خطة Vercel مؤهلة بعد مراجعة [حدود Vercel الرسمية](https://vercel.com/docs/cron-jobs/usage-and-pricing). لا تشغل مجدولين لنفس المهمة بلا ضرورة.

## الأسرار والإعدادات

| الإعداد | المصدر | مطلوب متى؟ |
|---|---|---|
| NEXT_PUBLIC_APP_URL | عنوان النشر | دائمًا |
| NEXT_PUBLIC_SUPABASE_URL / PUBLISHABLE_KEY | لوحة Supabase | كل تدفق بيانات |
| SUPABASE_SECRET_KEY | لوحة Supabase | worker وتهيئة حسابات وخدمة جلسات مجهولة محمية بملكية token |
| GEMINI_API_KEY / GEMINI_MODEL | Google AI Studio | تجربة Gemini الحية |
| TELEGRAM_BOT_TOKEN | BotFather | إشعار حي |
| CRON_SECRET | مولد أسرار عشوائي | endpoint العامل |
| QUOTE_SIGNING_SECRET | مولد أسرار | توقيع عروض checkout |
| RATE_LIMIT_SALT | مولد أسرار | HMAC مفاتيح حدود المعدل |
| APP_ENV | local/demo/production | فصل التشغيل |

الأسرار عشوائية طويلة ومستقلة لكل بيئة؛ لا القيم الافتراضية ولا reuse بين المشاريع. يتوقف checkout عند غياب إعداد مالي/قاعدة أساسي برسالة إعداد واضحة، بينما Gemini/Telegram يظهران حالة degraded للمشرف دون تحطيم المتجر.

## قائمة ما قبل العرض

- build ناجح، migrations مطبقة، seed موجود، لا login افتراضي منشور.
- تجربة العميل باللغتين واختبار كل دور.
- إرسال Telegram من عامل مجدول حي، وليس زر اختبار فقط.
- فحص fallback Gemini وfailed notification مع retry.
- noindex للديمو ونسخة احتياطية للبيانات التجريبية المهمة.
- سجلات بلا secrets/PII، مراقبة استهلاك المزودات.

## الاسترجاع

سجل deployment السابق وخطة migrations قبل كل إصدار. استرجاع واجهة Vercel لا يتراجع عن DB تلقائيًا. استخدم migrations متوافقة خلفيًا عند الإمكان، وخذ backup قبل تغيير بيانات. اختبر restore على مشروع معزول؛ خيارات الاحتفاظ وPITR تعتمد على خطة Supabase وتتحقق عند التشغيل. إذا إصدار فاشل: أوقف التغيير المؤذي، أعد الواجهة المتوافقة، ثم أصلح migration forward دون مسح البيانات. لا تشغّل seed reset في production.

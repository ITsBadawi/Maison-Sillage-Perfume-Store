# خطة الاختبار والقبول

هذه خطة قبول للنسخة الأولى. النتائج الفعلية وتاريخها وبيئتها مسجلة في [CURRENT_TASK](../plans/CURRENT_TASK.md): اجتازت النسخة المبنية محليًا 49 اختبار وحدة و31 اختبار متصفح مع Supabase وMailpit محليين، واختبارا تأكيد البريد نجحا منفصلين بإعدادهما الخاص. لا تشمل هذه النتيجة اتصالًا حيًا بـGemini أو Telegram، ولا نشرًا بعيدًا.

اختبارا تأكيد البريد في `tests/e2e/email-confirmation-live.spec.ts` يتطلبان تشغيل Supabase المحلي مؤقتًا مع `auth.email.enable_confirmations=true` و`RUN_CONFIRMATION_E2E=1`. نجحا على النسخة المحلية، ثم أُعيد الإعداد إلى `false` لتبقى حسابات الديمو قابلة للتسجيل الفوري. لا تشغّل هذه الخطوة على مشروع بعيد أو بيانات حقيقية.

## مستويات التحقق

| المستوى | الأداة | حالات أساسية |
|---|---|---|
| قواعد نقية | Vitest | حساب money، rounding، score، weights، ترتيب التعادل، transitions |
| مكونات | Testing Library | keyboard للاختبار، أخطاء form، اللغة والكتم |
| DB integration | قاعدة Supabase محلية + SQL tests | RLS، RPC، قيود، transactions، التزامن |
| E2E | Playwright | العميل والإدارة على ar/en وmobile/desktop |
| مزود خارجي | طلب حي محدود | Gemini structured output وTelegram في قناة الديمو |
| يدوي | متصفح وأجهزة | جودة الصور، خطوط عربية، تابلت، صوت، تجربة العرض |

## اختبارات حاسمة

1. مخزون SKU=1، طلبان متزامنان بمفتاحين مختلفين: نجاح واحد، الآخر STOCK_CHANGED، المخزون صفر، outbox واحد للطلب الناجح.
2. 10 طلبات بنفس مفتاح idempotency ونفس payload: order واحد وخصم واحد وحركة واحدة. نفس المفتاح مع payload مختلف: 409.
3. كوبون total_limit=1 مع شراءين متزامنين: redemption واحدة فقط. تحقق حد العميل وتاريخ انتهاء boundary بتوقيت UTC.
4. إلغاء قبل الشحن مرتين: إعادة كمية واستخدام كوبون مرة واحدة فقط. إعادة المخزون بعد المرتجع لا تحدث حتى فحصه.
5. إرسال price=1 أو خصم=100% أو fee=0 من العميل لا يغيّر حساب الخادم.
6. سعر أو رسوم تغيرت منذ quote: لا ينشأ طلب حتى عرض جديد وموافقة. تحقق expiresAt والتوقيع والمالك.
7. عميل A لا يقرأ طلب B أو بنوده أو نتيجته، حتى بمعرفة UUID أو رقم الطلب.
8. inventory_manager يضيف عطرًا لكنه يتلقى 403/منع RLS عند قراءة orders أو PII. orders_manager لا يغير المخزون مباشرة.
9. تعديل user_metadata.role لا يمنح صلاحية؛ تعطيل الموظف يمنع mutation التالي. لا يمكن تعطيل آخر Manager.
10. مثال score الموثق يعطي 87 و40؛ الأبعاد غير المقاسة لا تخفض النتيجة؛ المدخل نفسه يعطي ترتيبًا مطابقًا.
11. المنتجات draft/archived/out-of-stock/recommendation_disabled لا تدخل النتائج؛ ثلاث variants لمنتج واحد تعطي بطاقة واحدة.
12. ميزانية أو استثناءات لا تجد نتائج: صفر واضح، دون تخفيف سري للشروط. «لا تفضيل» للجميع لا ينتج نسبًا مختلقة.
13. Gemini يعيد ID غريبًا أو HTML أو سعرًا أو نسبة أو JSON غير صالح أو timeout: fallback بلا بطاقة خارجية ولا توقف السلة.
14. Telegram 429/500/timeout أو موت العامل بعد send: retry مع lease، لا فقد للطلب، والتكرار المحتمل يحمل نفس رقم الطلب.
15. مخزون نفد بعد التوصية: حالة عدم توفر وإعادة حساب اختيارية؛ checkout يمنع البيع الزائد.
16. نشر quiz version جديدة لا يغيّر أجوبة session بدأت بالقديمة.
17. فحص bundle وlogs لا يجد secrets ولا عنوان عميل كامل. ملفات upload غير مسموحة مرفوضة.

## إتاحة وأداء

keyboard كامل وfocus واضح وتباين وlabels ورسائل screen reader وzoom 200%. لا overflow أفقي للصفحة. جرّب reduced motion والصوت المعطل. قس الأداء على بيانات وصور الديمو في build منشور، وسجل الجهاز والشبكة والقياس؛ لا تكتفِ بـdev server ولا تعتبر Lighthouse مرة واحدة ضمانًا.

## خط CI المقترح بعد إنشاء التطبيق

`npm ci` → lint → typecheck → unit tests → build. DB integration وE2E على بيئة معزولة ببيانات seed وحسابات مؤقتة. أسرار الخدمات الخارجية لا تُتاح لكود PR غير موثوق. فحص تكامل Gemini وTelegram الحي يدوي محدود أو pipeline محمي قبل العرض؛ tests الاعتيادية تستخدم mocks لتجنب الكلفة وعدم الثبات.

## شرط الإصدار

لا عطل يمنع شراءً أو يعرض بيانات مستخدم آخر، لا فشل بصلاحيات الأدوار، لا overselling أو total خاطئ، ولا زر أساسي وهمي. يمكن قبول تحسين بصري ثانوي مع توثيقه، لكن لا استبدال التدفقات الحقيقية بفيديو. يُحفظ دليل مختصر بالنتائج والعيوب المتبقية في المهمة الحالية.
